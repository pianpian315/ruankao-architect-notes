    2.2 必背：6 部分质量属性场景（核心）¶

    每个质量属性场景由 6 个部分构成：

    编号 名称 含义 示例
    1 刺激源 Source 刺激的发源地 用户、内部系统、外部攻击者
    2 刺激 Stimulus 到达系统的事件 请求、故障、攻击
    3 制品 Artifact 被刺激的部分 系统、数据库、模块
    4 环境 Environment 系统运行状态 正常运行、降级、过载
    5 响应 Response 系统采取的动作 处理、记录、拒绝
    6 响应度量 Measure 量化指标 响应时间≤2秒、可用性≥99.99%

    必考题型：给一段描述，要求填入 6 部分的对应内容或判断属于哪个质量属性

    示例题（2019 真题改编）：

    "在系统正常运行情况下，系统在 1 秒钟内处理来自外部用户的 1000 个并发请求" - 刺激源：外部用户 - 刺激：1000 个并发请求 - 制品：系统 - 环境：正常运行 - 响应：处理请求 - 响应度量：1 秒钟内 / 1000 并发 - → 这是性能质量属性场景

    2.3 6 大质量属性详解¶

    ① 可用性 Availability¶

    关注：系统正常服务时间比例 度量：MTTF / MTBF / MTTR / 可用性百分比（99.9%、99.99%）

    典型战术（必背）： - 错误检测：命令/响应、心跳(Heartbeat)、异常检测 - 错误恢复：表决、主动冗余（热备）、被动冗余（温备/冷备）、备件、回滚、重试、降级 - 错误预防：从服务中删除（清除）、事务、进程监视器

    关键词识别：故障、宕机、恢复、容错、冗余、备份、心跳

    ② 性能 Performance¶

    关注：响应时间、吞吐量 度量：延迟、TPS、QPS、并发数

    战术： - 资源需求：减少计算开销、降低事件率、限制执行时间、限制队列大小 - 资源管理：引入并发、维持多个副本（数据/计算）、增加可用资源 - 资源仲裁：调度策略（FIFO、固定优先级、动态优先级、SJF）

    关键词：响应时间、吞吐量、延迟、并发、性能瓶颈、缓存、负载均衡、CDN、异步

    ③ 安全性 Security¶

    关注：抵抗攻击、保护数据 度量：检测/抵抗攻击的能力、恢复时间

    战术： - 抵抗攻击：用户认证、用户授权、维护数据机密性/完整性、限制暴露、限制访问 - 检测攻击：入侵检测系统 IDS - 从攻击中恢复：恢复=可用性战术；识别攻击者=审计追踪

    关键词：认证、授权、加密、防火墙、入侵检测、审计、CA 证书

    ④ 可修改性 Modifiability¶

    关注：变更的成本和难度 度量：变更时间、变更成本、变更影响范围

    战术： - 局部化变更：维持高内聚、抽象通用服务、预期期望变更 - 防止连锁反应：信息隐藏、维持现有接口、限制通信路径、使用中介 - 推迟绑定时间：运行时注册、配置文件、多态、组件替换、参数化

    关键词：扩展、修改、新增模块、配置化、解耦、热插拔

    ⑤ 可测试性 Testability¶

    战术：内置监视器、记录/回放、接口实现分离、依赖注入

    关键词：单元测试、自动化、Mock、覆盖率

    ⑥ 易用性 Usability¶

    战术：分离用户接口（MVC）、支持用户主动（取消、撤销、聚集、再使用）

    关键词：用户体验、操作便捷、撤销、引导、培训

    3 大核心输出（必考）：

    概念 定义 识别要点
    敏感点 Sensitivity Point 影响单个质量属性的架构决策 "为提高 X，采用 Y"
    权衡点 Tradeoff Point 影响多个质量属性的架构决策 "同时影响 X 和 Z"，常是矛盾权衡
    风险点 Risk 可能引起质量目标无法达成的决策 "可能导致..."、"存在风险"
    非风险点 Non-Risk 经过分析的好的架构决策 "明确合理"、"已验证"

    经典识别题套路（必考！）：

    题目给若干描述，让你填到敏感点/权衡点/风险点/非风险点

    判别口诀： - 描述涉及"提高/影响 1 个属性" → 敏感点 - 描述涉及"同时影响多个属性，需权衡"→ 权衡点 - 描述含"可能"、"风险"、"难以确定" → 风险点 - 描述明确"经过验证"、"合理"、"成熟" → 非风险点

    典型例题：

    ① "为提高响应速度，使用 Redis 集群作为缓存层" → 敏感点（仅影响性能） ② "采用主从同步复制，强一致性同时降低了写入性能" → 权衡点（同时影响一致性和性能） ③ "暂时无法估计第三方接口的响应时间稳定性" → 风险点 ④ "采用 Nginx 集群进行负载均衡，已在多个项目验证" → 非风险点

    2.5 效用树（Utility Tree）¶

    结构：根节点(效用) → 质量属性 → 属性细化 → 场景叶子节点 每个叶子标注 (重要性, 实现难度)：H/M/L

    示例： 效用 Utility ├── 性能 Performance │ ├── 数据延迟：在线交易响应≤2s (H, M) │ └── 事务吞吐：支持 5000 TPS (H, H) ├── 可用性 Availability │ ├── 硬件故障：故障 5min 内恢复 (H, L) │ └── 软件容错：服务降级时核心可用 (M, M) ├── 安全性 Security │ ├── 数据加密：敏感数据 AES 加密 (H, L) │ └── 访问控制：基于 RBAC 模型 (M, L) └── 可修改性 Modifiability ├── 接口扩展：新增 API≤2 人天 (M, L) └── 业务规则：配置化修改 (H, M)

    填空题套路：题目给场景描述，让你画或补全效用树（标 H/M/L）

    2.7.1 SAAM / ATAM / CBAM 三兄弟辨析（必考）¶

    三种架构评估方法是案例题与选择题高频辨析点，全称、关注点、使用阶段都要记牢。

    缩写 全称（英文） 中文 提出时间 核心关注
    SAAM Software Architecture Analysis Method 软件架构分析方法 1994（最早） 可修改性、功能性
    ATAM Architecture Tradeoff Analysis Method 架构权衡分析方法 1998 多质量属性权衡
    CBAM Cost Benefit Analysis Method 成本效益分析方法 ATAM 之后 ROI 投资回报率

    🎯 一句话记忆：

    "SAAM 看改、ATAM 看权衡、CBAM 看钱"

    • SAAM 早，先关注改不改得动（可修改性）
    • ATAM 晚，关注多属性的取舍（权衡）
    • CBAM 最后，关注改造值不值这个钱（ROI）

    使用先后顺序：SAAM → ATAM → CBAM（早期分析 → 多属性评估 → 经济性决策）

    英文助记： - SAAM = Analysis（分析） - ATAM = Tradeoff Analysis（权衡分析） - CBAM = Cost（成本）—— 看到 C 想到 Cost（钱）

    3.2 必备知识点¶

    ① 集群与负载均衡¶

    集群类型： - 高可用集群（HA）：主备/双活，故障切换 - 负载均衡集群（LB）：分摊请求 - 高性能集群（HPC）：并行计算

    负载均衡算法： | 算法 | 特点 | 适用 | |------|------|------| | 轮询 RR | 顺序分配 | 节点性能相近 | | 加权轮询 WRR | 按权重 | 节点性能不同 | | 随机 | 概率分配 | 简单负载 | | 最小连接数 | 选连接数少的 | 长连接业务 | | 最小响应时间 | 选最快的 | 性能敏感 | | 一致性哈希 | 节点变化影响小 | 缓存集群 | | IP Hash | 同 IP 落同节点 | 会话保持 |

    LVS 三种模式： - NAT：通过修改请求目的地址 - DR（直接路由）：性能最好（最常用） - TUN（IP 隧道）：跨网段

    ② 缓存¶

    多级缓存：浏览器 → CDN → Nginx → 应用层 → 分布式缓存(Redis) → DB

    缓存模式： - Cache Aside（旁路缓存，最常用）： - 读：先缓存，未命中读 DB 并写缓存 - 写：先更新 DB，再删除缓存 - Read/Write Through：缓存与 DB 同步 - Write Behind：异步写回 DB（高性能但有数据丢失风险）

    三大缓存问题（必考）： | 问题 | 原因 | 解决 | |------|------|------| | 缓存击穿 | 单个热点 key 过期，大量请求打到 DB | 互斥锁、永不过期、热点预热 | | 缓存穿透 | 查询不存在的数据，缓存层无效 | 布隆过滤器、空值缓存 | | 缓存雪崩 | 大量 key 同时失效 | 错峰过期（随机TTL）、多级缓存 |

    Redis 数据类型：String、List、Hash、Set、Sorted Set、Bitmap、HyperLogLog、Stream

    Redis 持久化： - RDB（快照）：定时快照，恢复快但可能丢数据 - AOF（日志）：每次操作追加，丢失少但文件大 - 混合持久化（Redis 4.0+）

    Redis 集群方案： - 主从复制 + 哨兵 - Cluster 集群（哈希槽 16384） - Codis（豌豆荚开源）

    ③ 消息队列¶

    作用（必背三要素）： 1. 解耦：生产者消费者独立 2. 异步：提高响应速度 3. 削峰：应对突发流量

    主流 MQ 对比： | MQ | 吞吐 | 延迟 | 特性 | 适用 | |----|------|------|------|------| | Kafka | 极高(百万级) | ms-s | 日志型、分区有序 | 大数据、日志 | | RocketMQ | 高(十万级) | ms | 事务消息、阿里 | 金融、电商 | | RabbitMQ | 中(万级) | μs | AMQP、灵活路由 | 企业、可靠传输 | | ActiveMQ | 较低 | ms | JMS、老牌 | 传统企业 |

    消息可靠性： - 不丢失：持久化 + ACK + 重试 - 不重复：幂等性、去重表、Token 机制 - 顺序消息：单分区、Hash 分区

    ④ 微服务架构¶

    核心特征： 1. 服务独立部署 2. 去中心化治理 3. 围绕业务能力组织 4. 智能端点和哑管道 5. 失败设计（Design for Failure） 6. 演进式设计

    ① 必背：E-R 图补全（高频）¶

    E-R 图四要素：实体（矩形）+ 属性（椭圆）+ 联系（菱形）+ 弱实体（双矩形）

    联系基数：1:1、1:N、M:N

    🎯 E-R 转关系模式口诀：

    "一对一爱合并、一对多向多放、多对多必独立"

    E-R 转关系模式规则： | 联系类型 | 转换规则 | 口诀 | |---------|---------|------| | 1:1 | 任一方加另一方主键作为外键，或合并为一张表 | 爱合并 | | 1:N | N 端加 1 端主键作为外键 | 向多放 | | M:N | 必须独立成新关系，主键 = 双方主键组合 | 必独立 | | 多元联系 | 独立成关系，主键 = 各方主键组合 | （同 M:N） | | 弱实体 | 独立成关系，主键 = 自身部分键 + 强实体主键 | 依附强实体 |

    🎯 候选键求解口诀（4 类划分法）：

    "L 必入、N 必入、R 必不入、LR 试探"

    类别 含义 处理
    L 类 只在函数依赖左部出现 必属候选键
    N 类 函数依赖中不出现的属性 必属候选键
    R 类 只在函数依赖右部出现 必不属候选键
    LR 类 左右都出现 求闭包试探

    💡 求出 L+N 属性集合后，求闭包能推出全部属性 → 该集合即为唯一候选键；否则需把 LR 类属性逐个加入试探。

    填空套路：题目给场景，要求： - 补充缺失的实体或联系 - 给出关系模式（含主键、外键） - 标识候选键

    📌 完整真题演示（学生选课系统）

    题干：某学校开发选课系统：学生(学号、姓名、专业)选修课程(课程号、课程名、学分)，每门课由一位教师(教师号、姓名)讲授，学生选课得到成绩。

    Step 1：识别实体与联系

    • 实体：学生、课程、教师
    • 联系：
    • 学生 ── M:N ──{选修}── 课程（联系属性：成绩）
    • 课程 ── N:1 ──{讲授}── 教师

    Step 2：套口诀转关系模式

    • 学生(学号, 姓名, 专业)
    • 教师(教师号, 姓名)
    • 课程(课程号, 课程名, 学分, 教师号*) ← 1:N 向多放，N 端加外键
    • 选修(学号*, 课程号*, 成绩) ← M:N 必独立，主键 = 双方主键组合

    约定：主键加下划线、外键标 *；外键引用关系：教师号 → 教师(教师号)、学号 → 学生(学号)、课程号 → 课程(课程号)。

    Step 3：候选键标注

    关系 候选键 判定
    学生 {学号} 学号 L 类必入
    教师 {教师号} 教师号 L 类必入
    课程 {课程号} 课程号 L 类必入
    选修 {学号, 课程号} 两者 L 类联合

    Step 4：范式判定（以"选修"表为例）

    • {学号, 课程号} → 成绩 ✅（联合决定成绩）
    • 学号 ⇏ 成绩，课程号 ⇏ 成绩 → 无部分依赖 → 满足 2NF
    • 无传递依赖 → 满足 3NF
    • 主属性也无部分/传递依赖 → 满足 BCNF ✅

    ② 必背：SQL 编写¶

    经典题型： 1. 创建表（含 PK、FK、约束） 2. 复杂查询（嵌套、关联、聚合） 3. 视图创建 4. 触发器/存储过程

    SQL 关键字必背： ```sql -- 创建表 CREATE TABLE 表名 ( 列名 类型 PRIMARY KEY, 列名 类型 NOT NULL, 列名 类型 UNIQUE, 列名 类型 DEFAULT 值, 列名 类型 CHECK (条件), FOREIGN KEY (列名) REFERENCES 主表(主键) ON DELETE CASCADE ON UPDATE CASCADE );

    -- 复杂查询模板 SELECT 列, 聚合函数(列) FROM 表1 [INNER|LEFT|RIGHT] JOIN 表2 ON 条件 WHERE 过滤条件 GROUP BY 列 HAVING 聚合条件 ORDER BY 列 [ASC|DESC] LIMIT N;

    -- 视图 CREATE VIEW 视图名 AS SELECT ... FROM ... WHERE ...; ```

    子查询： - 标量子查询（返回单值） - 列子查询（IN / NOT IN / ANY / ALL） - 行子查询（= / <>） - 表子查询（FROM 后） - 关联子查询（EXISTS / NOT EXISTS）

    ③ 必背：范式与函数依赖¶

    判定流程： 1. 找出所有函数依赖 2. 求候选键（4 类划分法，见 ① 节口诀） 3. 判断范式

    🎯 范式判定口诀：

    "一看分、二看部、三看传、B 看主属性"

    范式 判定要点 口诀 消除什么
    1NF 每个属性不可再分（原子性） 一看分 复合属性
    2NF 1NF + 非主属性完全依赖于码 二看部（消除部分依赖） 部分依赖
    3NF 2NF + 非主属性不传递依赖于码 三看传（消除传递依赖） 传递依赖
    BCNF 3NF + 主属性也无部分/传递依赖（左侧均含码） B 看主属性 主属性的异常依赖

    💡 递进关系：BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF（BCNF 最严格）

    模式分解： - 无损连接：分解后通过自然连接能恢复（必须保证） - 保持函数依赖：分解后所有原依赖仍成立（最好保证） - 分解原则：先保无损、再保依赖（无损是底线，依赖是加分项）

    必考二元分解判定：R 分解为 R1, R2 是无损连接 ⟺ - R1 ∩ R2 → R1 - R2，或 - R1 ∩ R2 → R2 - R1

    💡 口诀："交集决定差集" —— 两个子模式的交集属性能函数决定任一子模式的差集属性，即无损。

    ④ 反规范化¶

    何时反规范化： - 查询性能瓶颈 - 报表/统计场景 - 读多写少

    常用手段： 1. 增加冗余列（避免连接） 2. 增加派生列（预计算结果） 3. 重新组表（合并小表） 4. 分表（水平/垂直）

    反规范化代价：数据冗余、维护一致性成本高 → 通过触发器/应用层维护

    ⑤ 分布式数据库¶

    数据分片： - 水平分片（按行）：按某列范围/哈希拆分 - 垂直分片（按列）：按业务域拆分

    分库分表策略： - 分片键选择：访问频繁、分布均匀 - 分片算法：范围、哈希、一致性哈希

    分布式事务： - 2PC：准备 + 提交，强一致但阻塞 - 3PC：CanCommit + PreCommit + DoCommit - TCC（Try-Confirm-Cancel）：业务补偿 - Saga：长事务，本地事务串联+补偿 - 最终一致性：消息表、事件溯源

    分布式数据库分布性透明： - 分片透明：用户不感知分片 - 复制透明：用户不感知副本 - 位置透明：用户不感知物理位置 - 逻辑透明：用户不感知数据模型差异

    ⑥ 数据仓库与大数据¶

    OLTP vs OLAP： | 特性 | OLTP | OLAP | |------|------|------| | 用户 | 业务人员 | 决策者 | | 操作 | 增删改查 | 复杂分析 | | 数据量 | GB | TB-PB | | 事务 | 短小、并发高 | 长、并发低 | | 设计 | 规范化 | 反规范化（星型/雪花） |

    ETL：抽取 → 转换 → 加载

    数据仓库建模： - 星型模型：1 张事实表 + N 张维度表（最常用） - 雪花模型：维度表进一步规范化（节省空间但查询慢） - 星座模型：多张事实表共享维度

    数据湖 vs 数据仓库： | 维度 | 数据仓库 | 数据湖 | |------|---------|--------| | 数据 | 结构化 | 原始（结构化+半结构化+非结构化） | | Schema | Schema-on-Write | Schema-on-Read | | 用户 | 业务分析师 | 数据科学家 | | 成本 | 高 | 低 |

    Lambda 架构：批处理层 + 速度层 + 服务层（双路径） Kappa 架构：仅流处理（简化）

    Step 3：套答题话术 "本场景需要××（关键词），符合××模式的意图。 该模式的核心思想是××，能够××（解决的问题）。" ```

    🔥 易混淆模式对比（高频考点）：

    对比 区别
    适配器 vs 代理 适配器改变接口，代理保持接口
    装饰 vs 代理 装饰增强功能，代理控制访问
    外观 vs 适配器 外观简化已有接口，适配器转换接口
    策略 vs 状态 策略客户端主动选算法；状态对象内部自动切换
    观察者 vs 中介者 观察者一对多单向通知；中介者多对多集中协调
    责任链 vs 命令 责任链多个处理者依次判断；命令封装单个请求
    模板方法 vs 策略 模板方法用继承变细节；策略用组合换算法
    工厂方法 vs 抽象工厂 工厂方法造一类产品；抽象工厂造一族产品

    创建型（5 个）¶

    1. 单例 Singleton - 应用：连接池、配置管理、日志 - 实现要点：私有构造、静态实例、获取实例方法 java public class Singleton { private static Singleton instance; private Singleton() {} public static Singleton getInstance() { if (instance == null) instance = new Singleton(); return instance; } }

    2. 工厂方法 Factory Method - 应用：JDBC、日志框架 - 关键词："让子类决定实例化哪个类" java abstract class Creator { abstract Product factoryMethod(); } class ConcreteCreatorA extends Creator { Product factoryMethod(){return new ProductA();} }

    3. 抽象工厂 Abstract Factory - 应用：跨平台 UI、主题切换 - 关键词："产品族"、"多个相关产品"

    4. 建造者 Builder - 应用：StringBuilder、构造复杂对象 - 关键词："分步构建"、"Director + Builder"

    5. 原型 Prototype - 应用：对象克隆、Java 的 Cloneable - 关键词："克隆"、"复制创建"

    结构型（7 个）¶

    6. 适配器 Adapter - 应用：旧接口适配新接口、Stream/Reader 适配 - 关键词："接口转换" - 类适配器（继承）vs 对象适配器（组合，更常用）

    7. 桥接 Bridge - 应用：跨平台、形状-颜色独立变化 - 关键词："抽象与实现分离"、"两个变化维度"

    8. 组合 Composite - 应用：文件系统、组织架构、菜单 - 关键词："树形结构"、"部分-整体" - 一致对待叶子节点和组合节点

    9. 装饰器 Decorator - 应用：Java IO 流、日志增强 - 关键词："动态添加职责"、"包装" - 与继承的区别：动态、灵活、不污染原类

    10. 外观 Facade - 应用：库的统一入口、SDK - 关键词："简化接口"、"门面"

    11. 享元 Flyweight - 应用：字符串常量池、棋子复用、连接池 - 关键词："共享细粒度"、"内部状态/外部状态"

    12. 代理 Proxy - 应用：远程代理（RPC）、虚代理（懒加载）、保护代理（权限）、动态代理（Spring AOP） - 关键词："代理访问"

    行为型（11 个）¶

    13. 责任链 Chain of Responsibility - 应用：审批流、过滤器链（Filter）、Servlet - 关键词："链式处理"、"多个对象处理请求"

    14. 命令 Command - 应用：撤销/重做、任务队列、按钮事件 - 关键词："请求封装为对象"、"撤销" - 角色：Invoker、Command、Receiver

    15. 解释器 Interpreter - 应用：DSL、规则引擎、SQL 解释 - 关键词："文法解释"

    16. 迭代器 Iterator - 应用：集合遍历 - 关键词："遍历不暴露内部"

    17. 中介者 Mediator - 应用：聊天室、MVC 控制器、机场塔台 - 关键词："通过中介通信"、"减少多对多耦合"

    18. 备忘录 Memento - 应用：撤销操作、游戏存档 - 关键词："保存恢复状态"、"快照" - 角色：Originator、Memento、Caretaker

    19. 观察者 Observer - 应用：发布订阅、事件监听、MVC 中 Model→View - 关键词："一对多依赖"、"自动通知" - 推模型 vs 拉模型

    20. 状态 State - 应用：订单状态机、TCP 连接状态、电梯 - 关键词："对象行为随状态改变" - vs 策略：状态会自动切换、强调状态转换

    21. 策略 Strategy - 应用：促销算法、支付方式、排序算法 - 关键词："算法可替换"、"策略族" - vs 状态：策略由客户端选择、不会自动切换

    22. 模板方法 Template Method - 应用：钩子方法、抽象类基础流程 - 关键词："算法骨架"、"子类重写步骤"

    23. 访问者 Visitor - 应用：编译器 AST 处理、复杂数据结构操作 - 关键词："双分派"、"不修改类增加新操作" - 角色：Visitor、Element、ObjectStructure

    6.2 嵌入式系统知识点¶

    实时系统分类： - 硬实时：必须在截止期前完成（医疗、航天、工业控制） - 软实时：偶尔超时可接受（视频流、游戏）

    嵌入式系统层次： 1. 硬件层：处理器（ARM/MIPS/PowerPC）+ 外设 2. 中间层（BSP）：板级支持包，硬件抽象层 3. 系统软件层：嵌入式 OS + 文件系统 + 网络协议栈 4. 应用软件层

    嵌入式 OS 特性： - 可剪裁性：按需配置 - 强实时性 - 高可靠性 - 易移植性 - 低资源消耗

    任务调度算法： | 算法 | 类型 | 公式/特点 | |------|------|----------| | RM（速率单调） | 静态优先级 | 周期短优先级高 | | EDF（最早截止期） | 动态优先级 | 截止期近优先 | | LLF（最低松弛度） | 动态 | 松弛度=截止时间-当前-剩余执行 |

    RM 可调度判据：CPU 利用率 ≤ n(2^(1/n) - 1) - n=1: 100% - n=2: 82.8% - n=3: 77.9% - n=∞: 69.3%

    EDF 可调度判据：CPU 利用率 ≤ 100%

    优先级反转：低优先级持有锁阻塞高优先级 解决： - 优先级继承协议：低优先级临时继承高优先级 - 优先级天花板协议：访问资源时直接提到最高优先级

    6.3 系统集成¶

    集成层次： - 数据集成：ETL、数据复制 - 应用集成：消息、API、服务 - 业务集成：流程编排 - 表示集成：门户

    EAI 集成模式： - 文件传输：批量、松耦合 - 共享数据库：实时、紧耦合 - RPC：实时、紧耦合 - 消息：异步、松耦合（最推荐）

    ESB（企业服务总线）： - 核心功能：消息路由、协议转换、消息转换、安全、监控 - 模式：服务总线，集中式 - 主流产品：Mule、WSO2、Apache ServiceMix、阿里 EDAS

    SOA 治理： - 设计时治理：标准、规范 - 运行时治理：监控、SLA - 服务版本管理 - 服务生命周期管理

    6.5 物联网架构¶

    十、近年新增案例热点补充¶

    新热点通常不会脱离架构师主线，本质仍然考：质量属性、架构取舍、技术选型、风险与应对。

    10.1 Serverless 架构案例¶

    常见题干特征： - 业务流量波动大，存在明显峰谷 - 希望降低运维成本、按量付费 - 由 HTTP 请求、消息、文件上传、定时任务触发

    答题关键词： - 事件驱动、函数计算、API 网关、BaaS、自动弹性、按量计费 - 状态外置：数据库、缓存、对象存储 - 可观测性：日志、指标、链路追踪

    优点： 1. 自动扩缩容，适合突发流量 2. 无需管理服务器，降低运维成本 3. 按实际调用付费，资源利用率高 4. 便于快速开发轻量任务

    风险与应对： 1. 冷启动影响响应时间 → 预热、保留实例、拆分轻量函数 2. 厂商锁定 → 采用标准事件模型、隔离云厂商 SDK 3. 函数无状态 → 状态外置到 Redis/数据库/对象存储 4. 调试困难 → 完善日志、链路追踪和本地模拟环境

    10.2 云原生数据库 / 存算分离案例¶

    常见题干特征： - 数据量增长快，读写压力不均衡 - 希望计算资源和存储资源独立扩展 - 要求自动备份、容灾、高可用、低运维成本

    答题关键词： - 存算分离、弹性扩缩容、多副本、自动故障转移、备份恢复 - HTAP、NewSQL、分布式事务、全局一致性

    方案模板： 1. 存储层采用分布式共享存储，多副本保证可靠性 2. 计算层无状态化，按业务压力横向扩展 3. 读写分离和只读副本承担读压力 4. 自动备份、跨可用区部署，满足 RPO/RTO 5. 通过监控慢 SQL、连接数、锁等待优化性能

    风险与应对： - 跨节点事务复杂 → 控制事务边界，必要时采用最终一致 - 网络延迟增加 → 就近部署、缓存热点数据 - 成本不可控 → 设置资源配额、自动伸缩阈值和成本告警

    10.3 信创 / 国产化适配案例¶

    常见题干特征： - 政务、金融、能源等关键行业 - 要求国产 CPU、操作系统、数据库、中间件替换 - 关注自主可控、安全合规、平滑迁移

    答题框架： 1. 兼容性评估：梳理硬件、OS、数据库、中间件、第三方组件依赖 2. 分层适配：基础设施、数据层、应用层、接口层逐层替换 3. 数据迁移：结构迁移、数据校验、双写或灰度切换 4. 性能验证：基准测试、压力测试、容量评估 5. 安全合规：国密改造、等保要求、日志审计 6. 灰度上线：先非核心业务，再核心业务，保留回退方案

    常见风险： - SQL 方言不兼容 - 驱动和中间件 API 差异 - 性能下降 - 第三方组件不支持国产环境

    10.4 端-边-云协同案例¶

    常见题干特征： - 物联网、工业互联网、视频分析、车联网 - 要求低延迟、断网可用、减少带宽占用 - 终端数量多，数据实时性要求高

    职责划分： | 层次 | 职责 | |------|------| | 端 | 数据采集、设备控制、轻量推理 | | 边 | 实时处理、协议转换、缓存、局部决策 | | 云 | 全局调度、模型训练、海量存储、统一运维 |

    答题要点： - 边缘节点就近处理，降低时延 - 云端统一管理模型、策略和设备 - 边云断连时本地自治，恢复后数据同步 - 采用 MQTT/CoAP 等轻量协议接入设备

    10.5 AI 集群 / 高性能网络案例（了解型）¶

    常见题干特征： - 大模型训练、AI 推理平台、GPU/NPU 集群 - 关注训练效率、网络拥塞、节点故障恢复

    关键词： - GPU/NPU、RDMA、RoCE、AllReduce、高速互联、弹性调度 - 容器化调度、资源隔离、监控告警、故障迁移

    答题方向： 1. 计算层：GPU/NPU 池化，按任务调度资源 2. 网络层：RDMA/RoCE 降低通信延迟 3. 存储层：高吞吐并行文件系统或对象存储 4. 调度层：Kubernetes + AI 调度插件 5. 可靠性：节点健康检测、任务重试、检查点恢复

    10.6 性能测试与性能优化案例¶

    常见题干特征： - 要求设计性能测试方案 - 关注响应时间、吞吐量、并发数、资源利用率

    测试类型： - 负载测试：验证预期负载下能否满足指标 - 压力测试：找系统极限和瓶颈 - 容量测试：评估最大用户数/数据量 - 稳定性测试：长时间运行观察资源泄漏

    指标： - 平均响应时间、P95/P99 响应时间 - TPS/QPS、并发用户数 - CPU、内存、磁盘 I/O、网络 I/O - 错误率、超时率

    优化套路： 前端 CDN/压缩 → 网关限流 → 应用异步/线程池 → 缓存 → 数据库索引/读写分离 → 水平扩展。

    10.7 通信系统架构案例（补强）¶

    常见题干特征： - 出现 5G/工业网关/边缘站点/专网改造等背景 - 要求兼顾低时延、高可靠、可扩展与安全隔离 - 关注协议适配、链路冗余、QoS、故障切换

    答题关键词： - 分层设计（接入层/传输层/控制层/应用层） - 协议适配（MQTT/CoAP/HTTP/TCP/UDP） - QoS（时延、抖动、丢包率、带宽保障） - 高可用（双链路、主备切换、链路探活） - 安全（TLS、设备认证、访问控制、审计）

    标准答题骨架： 1. 架构分层：说明各层职责，避免耦合到单一协议或单一厂商设备。 2. 接入与协议：端侧按场景选择轻量协议，网关统一协议转换与数据标准化。 3. 传输与可靠性：关键链路双活/主备，心跳探测+自动切换，消息重传与去重。 4. 性能与 QoS：核心业务流量优先级更高，控制类报文优先保障时延。 5. 安全与运维：设备身份认证、链路加密、日志审计、统一监控告警。

    13.2 优先级反转完整例题（题 5 嵌入式必备）¶

    题干样式：

    任务 H（优先级 10）、M（优先级 5）、L（优先级 1）共享互斥资源 R： - t=0: L 启动，锁定 R，开始执行 - t=2: H 就绪，抢占 L - t=2.5: H 请求 R，被阻塞，L 继续持锁运行 - t=3: M 就绪，抢占 L 执行（与 R 无关） 分析存在什么问题，提出解决方案。

    标准答案骨架：

    (1) 问题诊断：

    发生优先级反转：高优先级 H 因等待 L 释放 R 而阻塞，但中优先级 M 抢占了 L 的执行，导致 H 间接被 M 阻塞，违反优先级调度原则，可能引起 H 错过截止期。

    (2) 解决方案对比：

    协议 机制 优缺点
    优先级继承协议 PIP L 锁 R 期间，若被 H 阻塞，则 L 临时继承 H 的优先级 → M 无法抢占 L → L 尽快释放 R 实现简单，但可能链式继承
    优先级天花板协议 PCP L 一获得 R 就立即提升到该资源的最高使用者优先级（天花板） 防止死锁与链式继承，但要预知最高优先级

    (3) 工程建议： - 缩短临界区 - 避免嵌套加锁 - 使用支持 PIP 的 RTOS（VxWorks、FreeRTOS）

    13.3 AOP（面向方面编程）案例补强（2019 真题）¶

    典型题干：日志、安全、事务等横切关注点散落在多个模块中，导致代码重复且难维护，如何重构？

    标准答案骨架：

    (1) 识别问题：横切关注点（Cross-Cutting Concerns）跨越多个模块，违反单一职责原则。

    (2) AOP 解决方案： - 切面 Aspect：把日志/事务/安全模块化为切面 - 连接点 Join Point：方法调用、方法执行 - 切入点 Pointcut：用表达式匹配需要织入的方法（如 execution(* com.xx.service.*.*(..))） - 通知 Advice：前置（@Before）、后置（@After）、环绕（@Around）、返回后（@AfterReturning）、异常后（@AfterThrowing） - 织入 Weaving：编译时织入（AspectJ）/ 运行时织入（Spring AOP 动态代理）

    (3) 效果： - 业务代码无侵入 - 横切关注点集中维护 - 符合开闭原则与单一职责

    (4) 与代理模式关系：Spring AOP 底层 = JDK 动态代理（接口）或 CGLIB（无接口）

    13.6 微服务拆分粒度判断（题 2 常考）¶

    题干样式：给出业务模块清单，要求拆分微服务并说明理由。

    拆分原则（DDD 方法）：

    1. 战略设计：识别核心域、支撑域、通用域
    2. 限界上下文 Bounded Context：每个上下文对应 1-2 个微服务
    3. 聚合根 Aggregate Root：维护一致性边界
    4. 服务粒度准则：
    5. 业务能力单一：围绕单一业务能力
    6. 数据私有：每服务独立数据库
    7. 团队规模：2-pizza team（< 8 人）
    8. 变更频率相近：高频变更不与稳定模块绑定

    常见拆分维度： - 按业务域：用户、订单、商品、支付、库存 - 按读写分离：查询服务 vs 命令服务（CQRS） - 按变化频率：稳定核心 vs 活动促销 - 按并发等级：高并发独立部署

    避免的反模式： - 过细："纳米服务"，运维负担过重 - 过粗：仍是单体只是换名字 - 共享数据库：违反微服务核心原则 - 同步链路过长：A→B→C→D→E（应改异步）

    13.7 缓存一致性方案对比（题 2 高频）¶

    方案 写策略 一致性 性能 风险
    Cache Aside（旁路） 先更 DB，再删缓存 最终一致 高 极短不一致窗口
    Read/Write Through 缓存代理写 DB 强一致 中 缓存层成为瓶颈
    Write Behind 异步写 DB 弱 极高 宕机丢数据
    双写 同时写 DB + Cache 不可靠 中 不推荐，易不一致

    一致性进阶方案： - 延迟双删：写 DB → 删缓存 → 延迟 N 秒 → 再删一次 - 订阅 binlog：通过 Canal 监听 MySQL binlog 自动更新缓存 - 分布式锁：写操作加锁，串行化更新

    13.8 分布式事务方案选型（题 2/题 3 常考）¶

    方案 一致性 性能 复杂度 适用
    2PC 强 低（阻塞） 中 跨库事务、传统场景
    3PC 强 较低 高 有超时要求
    TCC 强 中 高（业务侵入） 资金、订单核心业务
    Saga 最终 高 中 长事务（旅行预订）
    本地消息表 最终 高 低 通用异步
    MQ 事务消息 最终 高 中 RocketMQ 事务消息
    Seata AT 强 中 低（无侵入） 中后台一般场景
